23:T198a,<h1>walkthrough-pr</h1>
<p>Guide the user through a PR's changes <strong>one file per step</strong>. Never dump the whole diff. Each step covers a single file, in 2–3 lines, then <strong>stop and wait</strong> for the user to confirm they reviewed it before moving on.</p>
<h2>Procedure</h2>
<ol>
<li>
<p><strong>Resolve the diff.</strong> Determine the change set:</p>
<ul>
<li>If the user named a PR number, fetch it: <code>gh pr diff &#x3C;number> --name-only</code> for the file list, <code>gh pr diff &#x3C;number></code> for content.</li>
<li>Otherwise use the local branch vs base: <code>git diff --name-only &#x3C;base>...HEAD</code>. Detect the base instead of guessing: <code>git symbolic-ref refs/remotes/origin/HEAD</code> or <code>gh repo view --json defaultBranchRef -q .defaultBranchRef.name</code>; ask the user only if both fail.</li>
<li>Detect renames/moves (<code>git diff -M --name-status</code>) so a moved file isn't walked as a full delete + add. A pure move gets one cheap step: <code>moved X → Y, logic unchanged</code>, plus a line on any edits made in transit.</li>
<li><strong>Exclude test files</strong> from the walkthrough list. Drop paths that are clearly tests (e.g. <code>*.test.*</code>, <code>*.spec.*</code>, <code>__tests__/</code>, <code>test/</code>, <code>tests/</code>, <code>*_test.go</code>, <code>*_test.py</code>, snapshots/fixtures used only by tests). Mention in the opening line how many test files were skipped if any. If the user asks to include tests, walk them separately.</li>
<li><strong>Exclude generated and vendored files.</strong> Lockfiles (<code>package-lock.json</code>, <code>yarn.lock</code>, <code>pnpm-lock.yaml</code>, <code>Cargo.lock</code>, <code>*.lock</code>), build output (<code>dist/</code>, <code>build/</code>), <code>*.generated.*</code>, <code>*.min.*</code>, vendored deps, snapshots. Never walk a user through a lockfile diff — note it in one line ("lockfile updated for the new dep") and move on.</li>
<li><strong>Huge PRs (~30+ production files):</strong> don't walk every file. List the independent sub-flows with file counts and ask which to walk (default: riskiest / most central first). Within a chosen flow, proceed file-by-file as normal.</li>
</ul>
</li>
<li>
<p><strong>Order by data flow, not by file.</strong> Before presenting anything, read enough of the diff to understand <em>what the change actually does end-to-end</em>, then sequence the files to follow that flow — the path a request/value takes through the system. Never present in arbitrary, alphabetical, or <code>git</code>-listed order.</p>
<ul>
<li>Find the <strong>entry point</strong> of the change (the trigger: a route/handler, CLI command, event, user action, schema/migration that everything else builds on).</li>
<li>Follow the call chain / data movement outward from there: entry → validation/parsing → core logic/transform → persistence or side effects → response/output → consumers of that output. (Do not include test files in this sequence.)</li>
<li>When two files are peers in the flow, present the producer before the consumer (the thing that creates a value before the thing that reads it).</li>
<li>If the PR has independent sub-flows, walk one complete flow to its end before starting the next; announce the switch.</li>
<li>State this ordering rationale in one line up front so the user knows the spine they're following.</li>
</ul>
</li>
<li>
<p><strong>Announce the plan, briefly.</strong> One line naming the flow and file count (production files only). Example: <code>7 files (2 test files skipped). Following the request flow: route → validator → service → repo → response. Starting 1/7.</code> Do not summarize the files yet.</p>
</li>
<li>
<p><strong>Per-file step.</strong> For the current file output ONLY:</p>
<ul>
<li>Header line: <code>[N/total] path/to/file.ts</code></li>
<li>2–3 lines max on what changed and <em>why</em> it matters (the working, not a line-by-line dump). Name the key function/symbol and the behavior change.</li>
<li>Anchor it in the flow: state where this file sits in the chain and how data arrives here from the previous step and leaves toward the next (<code>receives the parsed body from the validator, writes it via repo.save()</code>). Each step should connect to the one before it, not stand alone.</li>
<li>If the file is large or non-obvious, point to the specific hunk worth reading (<code>see the change to handleAuth() around the token check</code>).</li>
<li>End with: <code>Reviewed? Reply to continue, or ask about this file.</code></li>
<li><strong>Then stop.</strong> Do not output the next file.</li>
</ul>
</li>
<li>
<p><strong>Wait for confirmation.</strong> Only advance when the user signals they're done (e.g. "next", "ok", "got it", "continue"). If they ask a question, answer it scoped to the current file, then re-prompt <code>Reviewed?</code> — do not advance on a question alone.</p>
</li>
<li>
<p><strong>Repeat</strong> in flow order until all files done.</p>
</li>
<li>
<p><strong>Closing.</strong> After the last file, give a 3–5 line synthesis that retraces the full flow end-to-end: how a value enters, moves through each file you covered, and exits. Call out cross-file interactions and anything risky to double-check. Offer next actions (approve, request changes, run tests).</p>
</li>
</ol>
<h2>Rules</h2>
<ul>
<li><strong>Skip test files.</strong> Walk production/source changes only; omit test paths unless the user explicitly asks to include them.</li>
<li><strong>Skip generated files.</strong> Lockfiles, build output, minified/generated code get a one-line mention at most, never a step.</li>
<li><strong>Order = data flow, always.</strong> Sequence files along the path data takes through the system (entry → transform → persist → output → consumers). Never alphabetical, never arbitrary. Each step links to the previous one.</li>
<li><strong>One file per message. No walls of text.</strong> If tempted to cover two files, split into two steps.</li>
<li>Keep each file's explanation to 2–3 lines. Detail comes on request, not by default.</li>
<li>Show the actual diff hunk only if the user asks or the change is subtle; otherwise describe.</li>
<li>Track progress with the <code>[N/total]</code> counter every step so the user knows how far in they are.</li>
<li>Never advance past a file the user hasn't confirmed.</li>
<li>Don't editorialize on style unless it affects correctness; this is comprehension, not review nitpicking.</li>
