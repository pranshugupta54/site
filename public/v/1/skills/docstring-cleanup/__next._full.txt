23:T15be,<h1>Docstring Cleanup — Decouple Docs from the Change</h1>
<h2>Why this matters</h2>
<p>A codebase lives independently of any single feature or PR. A docstring is read months later by someone who has never heard of the feature that introduced the code. Docstrings that narrate the change ("added as part of X", "new helper for the Y flow") rot instantly: the "change" becomes ancient history, but the text stays. Docs must describe <strong>what the code is and does now</strong>, in terms of the code itself — not the journey that produced it.</p>
<h2>The core rule</h2>
<blockquote>
<p>Write every docstring and comment as if the code had always existed. No reader should be able to tell, from the docs alone, which feature or PR introduced it.</p>
</blockquote>
<h2>Anti-patterns to find and fix</h2>
<p>Scan the diff (or the files touched) for these patterns:</p>
<ol>
<li>
<p><strong>Change narration</strong> — docstrings describing the diff, not the code:</p>
<ul>
<li>❌ <code>"""New helper added to support bulk export."""</code></li>
<li>❌ <code># Added this check as part of the retry-logic feature</code></li>
<li>✅ <code>"""Serialize records into the export wire format."""</code></li>
</ul>
</li>
<li>
<p><strong>Feature/PR/ticket references</strong> — coupling docs to project management artifacts:</p>
<ul>
<li>❌ <code>"""Handles pagination (see PR #482 / JIRA-1234)."""</code></li>
<li>❌ <code>"""Part of the new onboarding flow."""</code></li>
<li>✅ <code>"""Iterate over result pages, yielding one batch per request."""</code></li>
<li>Exception: a ticket reference is acceptable only when it documents a <em>permanent external constraint</em> (e.g. a vendor bug workaround) that the code cannot express.</li>
</ul>
</li>
<li>
<p><strong>Caller-specific docs on generic code</strong> — describing a utility in terms of its first caller:</p>
<ul>
<li>❌ <code>"""Format a timestamp for the invoice email."""</code> (on a generic <code>format_ts()</code>)</li>
<li>✅ <code>"""Format a timestamp as ISO-8601 with millisecond precision."""</code></li>
<li>The function's contract is its signature and behavior, not who happens to call it today.</li>
</ul>
</li>
<li>
<p><strong>Temporal language</strong> — "new", "now", "currently", "recently", "updated to", "no longer":</p>
<ul>
<li>❌ <code>"""Now uses the v2 client instead of the deprecated v1."""</code></li>
<li>✅ <code>"""Fetch via the v2 client."""</code> (or delete — the code already says this)</li>
</ul>
</li>
<li>
<p><strong>Reviewer-directed comments</strong> — text talking to the PR reviewer, not the next reader:</p>
<ul>
<li>❌ <code># Moved this here so the transaction wraps both writes</code></li>
<li>✅ <code># Both writes must commit atomically</code> (keep only if the constraint is non-obvious)</li>
</ul>
</li>
<li>
<p><strong>Redundant docstrings added for diff bulk</strong> — docs that restate the name/signature:</p>
<ul>
<li>❌ <code>"""Get the user by id."""</code> on <code>get_user_by_id(id)</code></li>
<li>Fix: delete. Absence of a docstring beats a noise docstring. Match the surrounding codebase's docstring density — don't document every helper in touched files when the rest of the codebase doesn't.</li>
</ul>
</li>
</ol>
<h2>Delegation</h2>
<p>This is mechanical pattern-matching work — it does not need a highly intelligent model. Feel free to delegate: spawn subagents (e.g. one per changed file or group of files, on a cheaper/faster model like Haiku) to scan and propose rewrites in parallel, then review and apply their proposals. Reserve your own judgment for the borderline cases (e.g. whether a ticket reference documents a permanent external constraint).</p>
<h2>Procedure</h2>
<ol>
<li><strong>Scope</strong>: get the set of changed files — <code>git diff main...HEAD --name-only</code> (or the diff/PR the user points at). Only touch docstrings/comments that the branch added or modified; leave pre-existing docs alone unless asked.</li>
<li><strong>Scan</strong>: for each changed file, read the added docstrings and comments. Also grep the diff for temporal/feature markers: <code>git diff main...HEAD | grep -inE '^\+.*(new |now |currently|recently|added|part of|this (pr|feature|change)|as part|no longer|updated to|refactored|moved)'</code> — treat hits as leads, not verdicts; judge each in context.</li>
<li><strong>Classify</strong> each flagged doc: rewrite (has real content buried in change-narration), delete (pure noise or restates the signature), or keep (already generic).</li>
<li><strong>Rewrite</strong> in place: describe behavior, contract, invariants, and non-obvious constraints — in the present tense, feature-agnostic, matching the file's existing doc style and density.</li>
<li><strong>Report</strong>: list each change as <code>file:line — before → after</code> (or "deleted") with one-line reasoning only where non-obvious.</li>
</ol>
<h2>What good docstrings say</h2>
<ul>
<li>The contract: inputs, outputs, side effects, error behavior.</li>
<li>Invariants and constraints the signature can't express ("must be called inside a transaction").</li>
<li>The <em>why</em> behind non-obvious choices — but a timeless why ("vendor API silently truncates >1MB payloads"), never a historical one ("changed because the old feature broke").</li>
</ul>
